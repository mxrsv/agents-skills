# Linear — solo-dev workflow with agents

Applies when working in the `mxrsv` workspace. This is the shared source of operating rules; templates and detailed configuration guidance may live in Linear. No need to call the MCP just to re-read these rules. The user's current instructions and the tools' permission limits always take precedence.

## Picking and claiming work

- **LW1.** The user works through the conversation; the agent manages the issues. Use the Linear MCP for supported operations. Use Computer Use only when the user explicitly asks for it in the current task; a missing MCP capability does not by itself grant permission to use Computer Use. Read the issue and its decision comments before editing; re-check the state before writing, and preserve metadata outside the scope of the change.
- **LW2.** The user locks the weekly goal and approves the set of work once. The agent may pull in additional small, clear work that serves the same goal; work outside the goal goes to Backlog, anything unclear gets `Needs decision` and a question. Changes in product direction, scope expansion or anything that incurs cost require approval.
- **LW3.** At session start or when asked to plan the day: look at held work and Blocked items first, then pick a feasible set within the weekly goal, state the expected outcome and continue. Today is the chosen set of issues — do not make the user create a "Today" issue; do not create issue copies, daily journals or fake due dates to represent the plan. Any automated schedule and the way the Today set is stored must be configured separately; the rules file does not create a scheduler.
- **LW4.** Each session executes one issue at a time; the next issue may be claimed once the previous one is waiting for review or Blocked. There is no cap on the total number of issues waiting for review; other sessions may work in parallel. Prioritize blockers that have been cleared; do not repeat old questions when there is no new information.
- **LW5.** The assignee stays `mxrsv`. Before starting, check for a claim comment; write the agent, session id and a timestamp with timezone, then re-read to detect contention. Comments/status are not an atomic lock: if someone else owns it, coordinate — do not seize work based on comment age. Take over only after confirming the previous session has stopped and reading its handoff.
- **LW6.** The handoff records progress, worktree/branch/PR, verification already run, next steps or blockers, and releases ownership. Do not move issues between teams to coordinate agents.

## Classification and decision rights

- **LW7.** Every work issue has exactly one Type: `Bug`, `Feature`, `Improvement`, `Maintenance` or `Verification`. Add acceptance criteria from context you are sure about; if the desired outcome is unclear, ask before implementing. Do not edit Done/Canceled issues just to add labels.
- **LW8.** Before editing code, pick exactly one Impact: `LOW` (local consequences, easy to recover), `MEDIUM` (affects several flows/modules, needs broad verification), `HIGH` (risk to data, security, operations, or hard to recover). Impact measures the consequence if it goes wrong; Priority measures urgency; a missing Impact does not mean safe. Reassess when new risk is discovered.
- **LW9.** Impact `HIGH`: investigation is allowed first; then present the approach, verification and recovery plan, and wait for the user's approval in the conversation before editing — even for an Urgent bug. A significant departure from the approved approach needs re-approval; small, reversible, in-scope decisions are yours to make.
- **LW10.** Data loss or a core function being unusable may preempt the weekly goal; report to the user immediately. Do not use the Urgent label to skip Impact approval or permission limits. Do not bulk-change priorities to hit a count target.

## Review, merge and completion

- **LW11.** Workflow: `Backlog` → `Todo` → `In Progress` → `Ready for Review` → `Done`; use `Blocked` when progress is impossible. Read the team's actual statuses; if a standard status is missing, report it — do not assume it has been configured.
- **LW12.** When the agent finishes implementation: record the result, verification evidence, PR/artifact links and what the user needs to approve; move to `Ready for Review`. The user approves in the conversation; the agent records the approved scope on the issue, then merges once the required verification and permissions are in place. If changes are requested, record the feedback, move back to `In Progress`, fix and re-verify before re-submitting for review.
- **LW13.** Permitted exception: an Urgent bug fix may be self-merged after verification if it has been confirmed that the merge does not trigger a deploy/release. Unsure about the effect of the merge → ask. Deploy/release still needs the user's approval; LW9 still applies. Linear admin rights are not a license to bypass repo or tool gates.
- **LW14.** `Done` only when the acceptance criteria and every required approval are met; a merged PR does not by itself mean Done. Still verifying → `In Progress`; waiting on a deploy or an external condition → `Blocked` with the reason. Do not enable auto-closing issues on PR merge if that removes this gate. The daily plan distinguishes "agent done, awaiting approval" from Done; never promise on the user's behalf for the approval part.
- **LW15.** At session end, report briefly: results, evidence, blockers and items awaiting approval. Interrupt immediately on an urgent incident or a decision that blocks progress; batch routine notifications. Do not open messaging channels outside the conversation without permission.

## Keeping the workspace consistent

- **LW16.** Keep the current teams as they are; do not merge/delete teams, move issues between teams or archive projects within this configuration. New issues go by product; Mxrsv is for shared/cross-product work and serves as the configuration reference team for new teams. Do not create teams just because a new repo or agent exists.
- **LW17.** Do not delete issues or cancel them for inactivity. Duplicates must link to the canonical issue; canceling work the user assigned needs approval. Agent reports go in comments on the related issue; create issues only for actions that need doing, and keep the old `Agent report` issues.
- **LW18.** The status/label names here are the agreed standard, not proof that the workspace has been updated. Configuration changes only within the assigned scope; for UI changes take before/after screenshots and stop to ask when the interface differs from the description. Do not set target dates, run schedules, or expand integration permissions that are still awaiting a decision.
- **LW19.** Everything an agent writes into Linear — issue titles, descriptions, comments, documents, project descriptions, label text — is in English, regardless of the conversation language or the active Output Style. Specs and plans are Linear content (D0, D4), so they are English too. Use the English section headings from the work-issue template (Goal / Scope and decisions / Acceptance criteria / Verification / Dependencies / Classification); if a template prefill is in another language, replace it. Forward-only: do not retro-translate existing issues except the passage being edited anyway. Code identifiers, paths and commands stay as they are.
