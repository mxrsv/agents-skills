# Workflow (W-rules)
- **W1.** Default to doing the work directly. Brainstorm/spec only when one of three thresholds is hit: (a) the request has several readings that lead to materially different, hard-to-reverse outcomes (otherwise pick the likeliest and state it); (b) it changes the architecture, data model, or an existing public contract (API / CLI), or changes or removes an existing UI flow (adding a new flow does not count); (c) the user explicitly asks. Below the threshold → just code.
- **W2.** Write a plan when the work spans multiple sessions / multiple commits, or the user requests one. A small, clear task needs no plan even if a spec exists. Single-session work uses plan mode instead of a plan file. Specs in `docs/specs/` own requirements; plans in `docs/plans/` own execution and reference the spec (D4); neither automatically requires the other. On a bug → use `diagnosing-bugs` before fixing (not `systematic-debugging`). Scale the investigation to the bug.
- **W4.** Before the first edit of a task, state in one line the pass/fail check that will show it is done: a test, typecheck, build exit code, or a screenshot beside the mock. Work with no such check (a UI direction, copy, marketing) uses a side-by-side against a named reference, then the owner's eye; no reference yet → ask for one (FE1). Report "done / fixed / passing" only after the check ran, with its command and output pasted as evidence. Once it and the gates the task triggers pass (skill `build-review`, and for UI the worst-case break-test and the owner-runtime screenshot in `kyant-ui-rules`), stop and report; name further improvements in one line instead of doing them.
  Why: the Claude Code docs make a pass/fail check the definition of done, and polishing past it was the owner's endless-revision loop (2026-11-25).
- **W8.** At the end of a task → delete the experimental/debug files you created.
- **W9.** Commands that change state in hard-to-reverse ways (delete, DB reset, deploy, migrate) → re-check that the evidence supports that specific action; unsure → ask. For changes with material data-loss, security or operational risk, present the approach, verification and recovery plan before editing and obtain approval unless that scope is already approved.
- **W11.** Before editing the first file → `git status --porcelain`. Work on the current checkout and branch by default, even when there are `M`/`??` files; leave changes outside the task's scope untouched. Do not create or switch to a worktree just because the checkout has uncommitted changes. When verification fails, check whether the failure belongs to the task's changes before concluding.
- **W14.** Resume from the spec's requirements where present and the task plan's approach, verification and latest handoff, then inspect the actual checkout before editing. Preserve other agents' changes. At handoff, record progress, checkout/branch/PR, observed verification, remaining work and blockers in the same plan. A merge is not acceptance: mark the task complete only when acceptance criteria and required approvals are met; report unrun gates. Merge/deploy/release need the user's authorization.
- **W19.** A reference that fits more than one thing ("yesterday's video", "the pending icon", "the landing page") → list the candidates (path or element, date, one line each) with a recommended pick. Local and reversible → act on the pick and name it in one line; outward-facing or costly (deploy, publish, delete, push) or candidates that differ materially → wait for the choice. Why: misread references were the top friction in the 2026-11-02 insights (20 misunderstood requests). Doc only.
- Owner decisions survive every handoff (spec, plan, build prompt, acceptance): follow skill `decision-traceability`.
- Risky features pass skill `build-review` and flow-changing mocks pass `mock-review` before the owner looks; triggers in skill `decision-traceability`.
