# Workflow (W-rules)
- **W1.** Default to doing the work directly. Brainstorm/spec only when one of three thresholds is hit: (a) the request has several readings that lead to materially different, hard-to-reverse outcomes (otherwise pick the likeliest and state it); (b) it changes the architecture, data model, or an existing public contract (API / CLI), or changes or removes an existing UI flow (adding a new flow does not count); (c) the user explicitly asks. Below the threshold → just code.
- **W2.** Write a plan when the work spans multiple sessions / multiple commits, or the user requests one. A small, clear task needs no plan even if a spec exists. Single-session work uses plan mode instead of a plan file. Specs in `docs/specs/` own requirements; plans in `docs/plans/` own execution and reference the spec (D4); neither automatically requires the other. On a bug → use `diagnosing-bugs` before fixing (not `systematic-debugging`). Scale the investigation to the bug; apply W13 to every finding, including read-only reviews.
- **W3.** Edit only within the task's scope. Out-of-scope work discovered (drive-by refactors, other bugs) → raise it, do not do it yourself.
- **W4.** Never report "done / fixed / passing" without running the verification command (test / typecheck / build / screenshot) and pasting the output as evidence.
- **W5.** Conventional commits with a scope — `type(scope): description`. One commit = one complete piece of work.
- **W8.** At the end of a task → delete the experimental/debug files you created; check every new file against the F-rules.
- **W9.** Commands that change state in hard-to-reverse ways (delete, DB reset, deploy, migrate) → re-check that the evidence supports that specific action; unsure → ask. For changes with material data-loss, security or operational risk, present the approach, verification and recovery plan before editing and obtain approval unless that scope is already approved.
- **W11.** Before editing the first file → `git status --porcelain`. Work on the current checkout and branch by default, even when there are `M`/`??` files; leave changes outside the task's scope untouched. Do not create or switch to a worktree just because the checkout has uncommitted changes. Always commit with `git commit -- <paths>`, never `git add -A` / `git commit -a`. When verification fails, check whether the failure belongs to the task's changes before concluding.
- **W13.** Evidence before conclusions: call a finding or root cause confirmed only with checkable evidence connecting the trigger, reachable execution path, and incorrect behavior. Include the command/steps and observed result, or a code-path proof with valid input. A provable defect is not automatically the cause of the reported incident. Without sufficient evidence, label it "Hypothesis — unverified", keep it separate from confirmed findings, and state the next discriminating check. Passing tests after a fix alone do not establish causality.
- **W14.** Resume from the spec's requirements where present and the task plan's approach, verification and latest handoff, then inspect the actual checkout before editing. Preserve other agents' changes. At handoff, record progress, checkout/branch/PR, observed verification, remaining work and blockers in the same plan. A merge is not acceptance: mark the task complete only when acceptance criteria and required approvals are met; report unrun gates. Merge/deploy/release need the user's authorization.
- **W15.** Skill suggestion — at the end of a task (never mid-task), if a procedure looks reusable, append ONE line at the end of `Result`/`Kết quả`: `💡 Skill candidate: <name> — <trigger> → <what it saves>`. Read `skills/skill-candidates/SKILL.md` (section "W15") for the triggers and rules before suggesting; suggest only, never create the skill without approval.
